# 技術架構與生成式 AI 應用

競賽規定：**僅限使用 AWS 服務提供之基礎模型**（Amazon Bedrock）。
本文件把這個限制當成設計條件，而不是事後補救。

---

## 1. Bedrock 上的實際限制（先確認，再設計）

Bedrock 是 AWS 代管的 Claude，**與第一方 Anthropic API 並非功能等價**。
影響我們架構的關鍵差異：

| 能力 | Bedrock | 對本專案的意義 |
|---|---|---|
| Vision（影像輸入） | ✅ | **掃描財報抽取可行** |
| PDF 文件輸入 | ✅ | 可直接丟 PDF（限 32MB / 600 頁）|
| Structured Outputs (`output_config.format`) | ✅ | **可強制 JSON schema**，抽取結果不用寫 parser |
| Prompt Caching（手動 `cache_control`） | ✅ | 同一份 prompt 重複抽 132 份可省成本 |
| Token counting | ✅ | 可事前估算成本 |
| **Message Batches API** | ❌ | ⚠️ **不能用批次半價**，須自建併發控制 |
| **Files API** | ❌ | ⚠️ 影像須 base64 內嵌，不能先上傳取 file_id |
| 自動 prompt caching | ❌ | 必須手動下 `cache_control` |
| Web search / fetch / code execution | ❌ | 輿情爬取要自己做（Lambda），不能用內建 web search |

**兩個 ❌ 直接改變工程做法**：

1. **沒有 Batches API** → 5,162 頁不能丟批次。要自己寫 worker pool
   （Step Functions Map state 或 SQS + Lambda 併發），並處理 429 退避。
2. **沒有 Files API** → 每次請求都要帶完整 base64 影像。這使得
   「只抽必要頁面」從優化變成**必要設計**（見 §3）。

模型 ID 在 Bedrock 需加 `anthropic.` 前綴，並使用 Mantle client：

```python
from anthropic import AnthropicBedrockMantle

client = AnthropicBedrockMantle(aws_region="us-west-2")
resp = client.messages.create(
    model="anthropic.claude-sonnet-5",   # 注意前綴
    max_tokens=8000,
    messages=[...],
)
```

> 定價依 AWS Bedrock 費率（與第一方 API 不同），須查 AWS Bedrock pricing 頁確認，
> 不要拿 Anthropic 官方定價當預算依據。

## 3. 抽取管線設計（成本與可信度）

### 3.1 只抽必要頁面

沒有 Files API，每頁都要 base64 內嵌，所以**頁面選擇就是成本控制**。
Phase 1 每份非營利財報只需 3 頁即可取得全部 P0 訊號：

| 頁 | 定位方式 | 產出欄位 |
|---|---|---|
| 資產負債表 | 關鍵字比對 | 現金、預收款項、準備金、餘絀 |
| 收支餘絀表 | 關鍵字比對 | 各科目 預算/決算/**執行率** |
| 附註一 一般概況 | 關鍵字比對 | 核定／實際招收人數、員工數、教保人員數、受託法人、契約期間 |

**132 份 × 3 頁 ≈ 400 次 vision 呼叫**（非 5,162 頁）。
以高解析影像約 4,784 tokens/頁估算，輸入約 190 萬 tokens——
規模完全可控，且可用 token counting 先估。

Phase 2 再擴至全量附註（關係人、會計師意見）。

### 3.2 用 Structured Outputs 而非「請回傳 JSON」

Bedrock 支援 `output_config.format`，可用 JSON Schema **強制**輸出結構，
不需要寫容錯 parser、不需要 retry-on-parse 迴圈。
金額欄位全部宣告為 `number`，並強制 `additionalProperties: false`。

同時在 schema 內要求模型回填 `source_page` 與 `confidence`，
讓低信心欄位自動進人工複核佇列。

### 3.3 Prompt Caching：把 schema 與指令放前面

抽取 prompt 的結構固定、只有影像在變。把 system prompt + schema 說明
放在 `cache_control` 斷點之前，影像放最後，132 份共用同一前綴。
（Bedrock 不支援自動快取，必須手動下斷點。）

### 3.4 可信度防線：不靠「相信 LLM」

評審必問「LLM 抽掃描檔的數字可信嗎」。三層防線：

1. **表內自我驗算**：`流動資產合計` 是否等於各項加總？
   `資產總計` 是否等於 `負債及餘絀總計`？（安溪 26,187,977 兩側相符）
   算不平 → 自動重抽。
2. **執行率反算**：`決算數 / 預算數` 是否等於報表印出的 `執行率`？
   這是報表自帶的 checksum，抽錯立刻現形。
3. **跨年雙盲對帳**：兩年重疊比較數（見 02 文件 §5）。

→ 可以對評審報出**量化的抽取準確率**，而不是「我們覺得還不錯」。

## 4. 生成式 AI 的四個落點（都是必要的，不是裝飾）

| # | 應用 | 為何非 GenAI 不可 |
|---|---|---|
| 1 | **掃描財報結構化** | 132 份掃描檔無文字層，傳統 parser 完全無解 |
| 2 | **裁罰文字嚴重度分級** | `law` 欄位是半結構化自由文字，需語意理解才能正規化成 (行為類型, 嚴重度, 受害對象) |
| 3 | **輿情訊號萃取** | 命題明確要求「納入社群輿論示警」；抱怨文本需分類與嚴重度判讀 |
| 4 | **RAG 稽查建議書** | 把「風險分數」翻譯成「引用法條與頁碼的可行動建議」——這是 Live Demo 的主秀 |

第 4 項是說服評審的關鍵。輸出不該是「安溪風險 0.73」，而是：

> **新北市安溪非營利幼兒園｜建議優先實地稽查**
> 1. 修繕購置費執行率僅 **15%**（核定 190,400 / 實支 28,074），
>    維護費 36% → 建議查驗遊具、消防與廚房設備現況。〔113學年度收支餘絀表〕
> 2. 人事費執行率 **88%**（少支 1,617,183 元），但實際招收 118/120 名 →
>    建議調閱教保人員編制表，核對《幼兒教育及照顧法》師生比。〔附註一〕
> 3. 行政管理費執行率 **100.0%**（325,932 元，與預算完全相同），
>    為全表唯一足額執行科目 → 建議檢視受託法人費用計算依據。
> 4. 業務發展準備（負債）較準備金（資產）短少 **2,200,000 元**，
>    且同年本期餘絀為 −1,988,771 元 → 建議說明提列與動支情形。
>
> ⚠️ 第 4 點需先確認非營利園準備金會計慣例，系統標為「待人工判讀」。

每一條都有金額、來源頁、對應動作。這是「AI × 鑑識會計」該有的樣子。

## 5. 服務對應表

| 層 | 服務 | 說明 |
|---|---|---|
| 儲存 | **S3** | `raw/` `interim/` `processed/`，raw 開版本控管 |
| 編排 | **Step Functions** | Map state 控併發（無 Batches API，須自控）|
| 運算 | **Lambda** | 頁面定位、公校文字抽取、特徵計算 |
| 模型 | **Bedrock**（Claude Sonnet 5 主力抽取 / Opus 5 判讀與生成） | 抽取用量大走 Sonnet；建議書生成走 Opus |
| OCR 備援 | **Textract** | 純表格頁的交叉驗證來源（第二意見）|
| 特徵庫 | **DynamoDB** | 機構主檔 + 特徵 + 分數，單表設計 |
| 分析 | **Athena / Glue** | 對 S3 parquet 做同儕分位數計算 |
| RAG | **Bedrock Knowledge Base** + OpenSearch Serverless | 法規（幼照法、非營利園實施辦法）＋財報附註 |
| 排程 | **EventBridge** | 每日更新裁罰／輿情 |
| 前端 | **App Runner / Amplify** | Streamlit 或 React 儀表板 |
| 護欄 | **Bedrock Guardrails** | 防止對特定機構產生無證據指控 |

**模型分工的理由**：抽取是高量、結構化、可驗算的任務 → Sonnet 5 足夠且便宜；
建議書生成要跨源推理並引用法規 → Opus 5。這個分工要在簡報講清楚，
它展現我們理解成本結構，而不是全部無腦用最大模型。

## 6. 倫理與治理（本題必須主動處理）

這個系統會對真實幼兒園貼上「高風險」標籤，影響其招生與聲譽。
設計上必須內建下列限制，且應在簡報明講：

1. **輸出定位為「稽查優先序」，不是「違法認定」**。用詞全面使用
   「建議查核」而非「疑似不法」。
2. **每個分數都要能展開到原始頁面證據**。無法追溯來源的訊號不得計分。
3. **模型不確定時標「資料不足」，不標「低風險」**。
   新設園（僅 1 年財報）尤其如此——沒有基線不等於安全。
4. **輿情訊號權重須低於裁罰與財報**，且不得單獨觸發高風險
   （社群發文可被惡意操作，這是可預見的攻擊面）。
5. **不公開對外揭露個別機構分數**，僅作為主管機關內部排程工具。
6. **人工覆核為必要環節**，系統定位為決策輔助而非自動裁決。
